## 1 OLTP

**โค้ด (oltp_demo.py):**
```python
cur = con.execute(
    "UPDATE orders SET status='PAID' WHERE order_id='O1004' AND status='PENDING'"
)
con.commit()
print('Rows updated:', cur.rowcount)
```

**ผลรันสองรอบ:**
```
--- RUN 1 ---
Before: [('O1004', 'PENDING')]
Rows updated: 1
After: [('O1004', 'PAID')]
--- RUN 2 ---
Before: [('O1004', 'PAID')]
Rows updated: 0
After: [('O1004', 'PAID')]
```

**คำอธิบาย:**
- รอบแรกแก้ไข **1 แถว** (PENDING → PAID) รอบที่สองแก้ไข **0 แถว** เพราะเงื่อนไข `status='PENDING'` ไม่เป็นจริงอีกต่อไป
- ต้องมีเงื่อนไข `status` เพราะทำให้คำสั่งเป็น **idempotent** (รันซ้ำกี่ครั้งก็ปลอดภัย) และป้องกันการเปลี่ยนสถานะย้อนกลับ เช่น เผลอรันซ้ำตอน order ถูก CANCELLED ไปแล้ว หากมีแค่ `WHERE order_id='O1004'` ระบบจะเขียนทับสถานะทุกครั้งไม่ว่าสถานะปัจจุบันจะเป็นอะไร
- กิจกรรมนี้เป็น **OLTP** ทั้งที่มี SELECT อ่านสถานะด้วย เพราะแก่นของงานคือ **ธุรกรรมเดี่ยว เปลี่ยนสถานะปัจจุบันของระเบียนเดียว (single-row write, current-state)** ซึ่งเป็นลักษณะของระบบปฏิบัติการ (transactional processing) ไม่ใช่การอ่านข้อมูลจำนวนมากเพื่อวิเคราะห์แนวโน้มแบบ OLAP การ SELECT ที่นี่เป็นเพียงการตรวจสอบก่อน/หลัง ไม่ใช่การ aggregate ข้ามหลายแถว

**คำอธิบายเพิ่ม:** การเปลี่ยน `oltp.db` **ไม่ทำให้** ยอดใน `warehouse.db` เปลี่ยนทันที เพราะเป็นฐานข้อมูลคนละไฟล์ ไม่มีการเชื่อมโยงอัตโนมัติ (README ระบุชัดว่า oltp.db แยกจากคลังข้อมูลและไม่มี ETL อัตโนมัติ) ระบบจริงควรมีกระบวนการ **ETL** (Extract–Transform–Load) หรือ CDC (Change Data Capture) ที่ทำงานเป็นรอบ (batch เช่นทุกคืน) หรือ near-real-time เพื่อดึงสถานะ/ธุรกรรมจากระบบ OLTP มาปรับปรุง fact table ใน Data Warehouse

## 2 Grain และ Star Schema

**Star Schema:**
```
                dim_date (PK: date_key)
                       |
                       | 1:N
dim_product (PK: product_key) --1:N-- fact_sales (PK: order_id, line_no)
                       |            FK: date_key, product_key, store_key
                       | 1:N
                dim_store (PK: store_key)
```
- `fact_sales` มี PK ผสม `(order_id, line_no)` และ FK ไปยัง `dim_date.date_key`, `dim_product.product_key`, `dim_store.store_key`
- ความสัมพันธ์เป็น **1 dimension : N fact rows** เสมอ (เช่น 1 วันมีได้หลายแถวขาย, 1 สินค้าขายได้หลายแถว)

**Grain:** 1 แถวใน `fact_sales` หมายถึง **สินค้า 1 รายการ (1 line item) ภายใน 1 ออเดอร์ ณ วันที่/สาขาหนึ่ง** เช่น `O1001` มี 2 แถว (line_no 1 = Tea, line_no 2 = Cookie) เพราะออเดอร์เดียวกันซื้อสินค้า 2 ชนิด แต่ละชนิดคือ 1 แถวของ grain

**q01.sql:**
```sql
SELECT COUNT(*) AS line_count, COUNT(DISTINCT order_id) AS order_count,
       SUM(quantity) AS units, SUM(amount) AS revenue
FROM sales;
```
**ผล:** line_count=8, order_count=6, units=23, revenue=1,390 บาท — ตรงกับที่ README ระบุ (8 รายการ, 6 ออเดอร์, 1,390 บาท) และตรงกับการเปิด `warehouse.csv` ดูจำนวนแถว

**2.3 Dimensions/Measures/Hierarchy:**
- **Dimensions (3):** เวลา (dim_date), สินค้า (dim_product), สถานที่ (dim_store)
- **Measures (2):** `quantity` (additive), `amount` (additive)
- **Hierarchy เวลา:** year → month → full_date
- **Hierarchy สถานที่:** region → province → store_name
- **ทำไม `unit_price` ไม่ควรบวกเป็นยอดขาย:** `unit_price` เป็น **ราคาต่อหน่วย** ไม่ใช่ยอดขาย การ SUM ราคาต่อหน่วยข้ามหลายแถวไม่มีความหมายทางธุรกิจ (เช่น ราคาต่อชิ้น 50+80 บาท ไม่ใช่ยอดขายรวม) ต้องคูณด้วย `quantity` ก่อนจึงจะรวมกันได้อย่างถูกต้อง (`amount = quantity × unit_price`) — เป็นตัวอย่างว่าคอลัมน์ตัวเลขไม่ใช่ทุกตัวที่เป็น additive measure

**ผลตรวจที่ได้:** จำนวนรายการ 8 จำนวนออเดอร์ 6 จำนวนชิ้น 23 ยอดขายรวม 1,390 บาท

## 3 OLAP Query

| Query | Operation | ผลลัพธ์สั้นๆ |
|---|---|---|
| q02 revenue by month | **Roll-up** (สรุปจากวันเป็นเดือน) | 2026-08=490, 2026-09=900 |
| q03 revenue by province | **Slice/Dice** (เพิ่มมิติสถานที่) | Bangkok=850, Chonburi=540 |
| q04 revenue by full_date (Sep) | **Drill-down** (ลงรายละเอียดในมิติเวลา) | 09-09=360, 09-10=300, 09-11=240 |
| q05 revenue by product (Drink only) | **Slice** (ตรึง category='Drink') | Tea=750 |
| q06 revenue by category, region (Drink/Snack, East) | **Dice** (กรอง 2 มิติ, แสดง 2 มิติ) | Drink/East=300, Snack/East=240 |
| q07 revenue by month (Aug–Sep, filtered) | **Slice + Having filter** | เฉพาะ 2026-09=900 ผ่านเกณฑ์ >500 |
| q12 revenue by province × month | **Drill-down** จาก q03 | รายละเอียดต่อเดือนของแต่ละจังหวัด |

**ก. ผลต่างของ q03 กับ q04:** q03 เพิ่ม "มิติสถานที่" ทำให้เห็นยอดขายแบ่งตามจังหวัด (มิติเดียวจากมิติเวลาเดิม) ส่วน q04 ยังอยู่ในมิติเวลาเดิมแต่ **เจาะรายละเอียดขึ้น** จากระดับเดือนเป็นระดับวัน (drill-down) — q03 คือการสลับ/เพิ่มมิติ ส่วน q04 คือการลงรายละเอียดในมิติเดิม

**ข. q07:** เงื่อนไข "จะรวมเดือนไหนบ้าง" (`month IN (...)`) ต้องอยู่ใน **WHERE** เพราะเป็นการกรองแถวก่อน GROUP BY ส่วนเงื่อนไข "ยอดรวมต้องเกินเท่าไร" (`SUM(amount) > 500`) ต้องอยู่ใน **HAVING** เพราะเป็นการกรองหลังการ aggregate (SUM ยังไม่มีค่าจนกว่าจะ GROUP BY เสร็จ)

**ค. q12 รวมกันแล้วเทียบกับ q03:** เมื่อรวม revenue ของ q12 ตาม province (รวมทุกเดือนของจังหวัดเดียวกัน) ต้องได้เท่ากับค่า revenue ของจังหวัดนั้นใน q03 พอดี (Bangkok: 310+540=850 ✓, Chonburi: 180+360=540 ✓)

**จุดตรวจ:** ยอดรายเดือนรวมกัน (490+900=1,390) เท่ากับยอดทั้งชุดใน q01 (1,390) ✓ และยอดรายวันเดือนกันยายน (360+300+240=900) เท่ากับผล Slice เดือนกันยายนใน q02 (900) ✓

**assert ผล P3:** `grand_total (1390) == df['amount'].sum() (1390)` → ผ่าน (`AssertionError` จะไม่เกิดขึ้น) — เลือกเฉพาะเซลล์ `p1.loc["Total","Total"]` เท่านั้น ไม่ใช้ทุกเซลล์ที่ชื่อ "Total" เพราะแถว Total และคอลัมน์ Total ต่างก็เป็นผลรวมย่อยอยู่แล้ว การเอาไปรวมกันอีกจะนับซ้ำ

**ทดลองข้อผิดพลาด (ลบ aggfunc):**
```
month     2026-08  2026-09
Bangkok     155.0    270.0
Chonburi     90.0    180.0
```
Bangkok เดือนกันยายนได้ **270** เพราะ `pivot_table` ค่าเริ่มต้นของ `aggfunc` คือ **"mean" ไม่ใช่ "sum"** เซลล์นั้นมี 2 แถวดิบคือ Tea 300 บาท กับ Cookie 240 บาท ค่าเฉลี่ยของสองแถว = (300+240)/2 = 270 ซึ่งไม่ใช่ยอดขายรวมที่ต้องการ (ที่ถูกต้องคือผลรวม 540 บาท) การแก้คือใส่ `aggfunc="sum"` กลับเข้าไปให้ตรงกับคำถาม "ยอดขายรวม"

**ข้อแตกต่างของ sum กับ mean:** `sum` ตอบคำถาม "ยอดขายรวมทั้งหมดของกลุ่มนั้นเท่าไร" ส่วน `mean` ตอบคำถาม "โดยเฉลี่ยแต่ละแถว/รายการมีมูลค่าเท่าไร" ใช้ผิดจะทำให้ยอดขายที่รายงานต่ำกว่าความเป็นจริงมาก โดยเฉพาะเมื่อมีหลายแถวต่อเซลล์

**คำถามชวนคิด:** ถ้าเพิ่มเดือนตุลาคม SQL แบบ `CASE WHEN month='2026-08' ...` / `CASE WHEN month='2026-09' ...` **จะไม่** สร้างคอลัมน์ตุลาคมให้เอง ต้องเพิ่ม `CASE WHEN month='2026-10' THEN amount ELSE 0 END AS oct` เองในโค้ด (คอลัมน์ถูกกำหนดตายตัวตอนเขียน SQL) ในขณะที่ pandas `pivot_table(columns="month", ...)` จะ**สร้างคอลัมน์ใหม่ให้อัตโนมัติ**ตามค่าที่มีจริงในข้อมูล เพราะ pandas สร้างคอลัมน์แบบ dynamic จากค่า distinct ของ column ที่ระบุ (ยืนยันจากผลรัน `challenge.py` ที่มีคอลัมน์ 2026-10 โผล่มาเองโดยไม่แก้โค้ด)

## 5 ตรวจความถูกต้อง

**q09.sql (UNION ALL):**
```
month     revenue
2026-08   490
2026-09   900
ALL       1390
```
การนำทุกแถวมารวมกันใหม่ (`UNION ALL` ของยอดรายเดือน) แล้วมีแถว "ALL" แยกที่คำนวณจากข้อมูลดิบอีกครั้ง เป็นการ **cross-check** ว่าการ GROUP BY ไม่ทำให้ข้อมูลหายหรือซ้ำ — 490+900 ต้องเท่ากับ 1,390 พอดี (ผ่าน)

**q10.sql (AOV):**
```
revenue  orders  aov     avg_line
1390     6       231.67  173.75
```
- **AOV** = SUM(amount) / COUNT(DISTINCT order_id) = 1390/6 = 231.67 บาท/ออเดอร์ — หน่วยคือ "บาทต่อออเดอร์"
- **AVG(amount)** = 1390/8 = 173.75 บาท/บรรทัด — หน่วยคือ "บาทต่อ 1 line item"
- ทั้งสองต่างกันเพราะตัวหารต่างกัน (จำนวนออเดอร์ vs จำนวนบรรทัดสินค้า) ใช้ AVG(amount) แทน AOV จะได้ค่าต่ำกว่าความเป็นจริงเมื่อออเดอร์มีหลายรายการต่อใบ

**q11.sql (ก่อน/หลัง JOIN):**
```
fact_rows  view_rows  fact_revenue  view_revenue
8          8          1390          1390
```
จำนวนแถวและยอดรวมตรงกันทั้งก่อน (fact_sales) และหลัง (sales view) JOIN และ `PRAGMA foreign_key_check` ไม่พบข้อผิดพลาด — ถ้ามี **คีย์ซ้ำในมิติ** (เช่น product_key ซ้ำในสองแถวของ dim_product) การ JOIN จะทำให้แถวใน fact ถูก**ทวีคูณ** (fan-out) ทำให้ยอดรวมสูงเกินจริง ส่วน **FK ที่หายไป** (เช่น fact อ้าง store_key ที่ไม่มีใน dim_store) จะทำให้แถวนั้นหายไปจาก INNER JOIN ทำให้ยอดรวม**ต่ำกว่าความเป็นจริง**

**5.4 ตัวอย่างการรวม:**
- **Additive** (รวมได้ทุกมิติ): `amount` (ยอดขาย) — รวมข้ามวัน สินค้า สาขา ได้หมด
- **Semi-additive** (รวมได้บางมิติ ไม่รวมข้ามเวลา): สต็อกสิ้นวัน (inventory on-hand) — รวมข้ามสาขา/สินค้าได้ แต่รวมข้ามวันไม่ได้ (ต้องใช้ค่าล่าสุดหรือค่าเฉลี่ย ไม่ใช่ SUM ข้ามวัน)
- **Non-additive** (รวมข้ามมิติใดๆ ไม่ได้เลย): AOV (ค่าเฉลี่ยต่อออเดอร์) — จะรวม AOV ของหลายเดือนตรงๆ ไม่ได้ ต้องกลับไปคำนวณจาก SUM(amount)/COUNT(DISTINCT order_id) ใหม่ทุกครั้งที่เปลี่ยนช่วงเวลา (ดู Bonus A: ค่าเฉลี่ยของ AOV รายเดือน ≠ AOV รวมทั้งช่วง)
